Crew roster

One role, one file, one job. A CEO role sits above the line and can run the whole company end to end for a single goal — "ship and sell app X this week" — without a human dispatching each station by hand.

CEO

Orchestrates the full company toward one business goal — sales, marketing, and the whole product team below.

Researcher

Niche and market validation — is there real demand before anything gets built.

BA

Backlog analysis and sprint planning — prioritizes by impact, breaks work into tasks.

PM

Coordinates Dev, Designer, UX, QA and Release into one pipeline per app.

Dev

Builds, compiles, and archives — owns the actual codebase and the build system.

Designer

Screens, flows, onboarding and paywall layout.

UX

Independent review of the Designer's work — accessibility, navigation, platform guideline fit.

QA

Mandatory gate. Tests like a user, not a compiler, before anything reaches Release.

Ship-critic

Mandatory gate. Biased toward "blocked" — reconciles what was promised against what was actually delivered.

Release

Owns the App Store Connect submission — metadata, screenshots, the checklist, rejection handling.

ASO

Keyword research, store metadata, and localization for discoverability.

Marketing

Positioning, launch content, landing pages, and the press kit.

Growth

Revenue, retention and paywall optimization once the app is live.

Inspection criteria — "shipped"

Every station reports against this, not against commit counts. All three, or it isn't shipped yet.

Pass · 1 of 3

Store-approved

The version is live and buyable in App Store Connect — not "submitted," not "in review."

Pass · 2 of 3

Paywall live

The offering is published and a real sandbox purchase has been run end to end: paywall → purchase → entitlement granted → still there after relaunch.

Pass · 3 of 3

Stranger install

At least one organic install from someone who has never heard of the project directly from its builder.

"Code written," "submitted for review," and "waiting for review" all read as progress on the line — none of them close the ticket.

Sheet 5 / 5

Field notes

The lessons that were expensive to learn once and cost nothing to know in advance.

  1. 01
    Simulator only for automated builds.
    A physical-device target drags code signing and provisioning into every build loop — the simulator sidesteps both.
  2. 02
    Never hand-edit the generated project file.
    If a project is generated from a spec file, the generator will silently clobber a hand edit on the next run — edit the spec.
  3. 03
    A 403/404/409 on a portal-only operation means stop, not retry.
    Some App Store Connect actions are deliberately API-blocked; retrying just burns calls against a door that was never going to open.
  4. 04
    Never retry a failed submission call.
    A server error mid-submission can still create the submission — a retry risks a second, orphaned one instead of a clean failure.
  5. 05
    Paywall configuration existing is not proof it works.
    Only a completed sandbox purchase — through to a surviving entitlement after relaunch — actually proves the money path.
  6. 06
    Clean build artifacts before an archive build.
    Stale intermediate products are a leading cause of failures that have nothing to do with the code just written.
  7. 07
    Two failures on the same approach is a mandatory pivot.
    A third attempt at an approach that has failed twice is rarely a fix — it's the same mistake with more patience.
  8. 08
    "It builds" and "it works" are different QA passes.
    A compiler pass certifies syntax, not the flow a real user takes through the screens.
  9. 09
    Bias the pre-submission reviewer toward blocking, not helping.
    A reviewer optimizing to be agreeable will wave through the exact gaps a submission gate exists to catch.
  10. 10
    One app on the simulator at a time for screenshots.
    A second installed app can appear in the frame or steal focus, and the mistake isn't visible until the screenshot is already captured.
  11. 11
    Cap work-in-progress across the portfolio.
    An agent team will happily start ten apps at once; nothing stops it from doing that except a rule that explicitly says not to.
